# Исправление смены Telegram-аккаунтов на одном устройстве

## Причина

Предыдущий клиент брал bearer из общего localStorage и проверял только telegramVerified. Если сессия уже была подтверждена другим Telegram-аккаунтом, свежие initData текущего аккаунта не сверялись до загрузки истории и профиля. Сервер при этом корректно отдавал данные владельца bearer, но клиент ошибочно выбирал старую сессию. В результате на общем устройстве могли отображаться история, профиль и функции менеджера первого аккаунта. Предыдущие тесты проверяли изоляцию владельцев разных токенов, но не этот путь выбора токена.

## Изменения

При каждом входе live-клиент отправляет текущие сырые initData на сервер ДО запроса профиля/истории. Подпись и свежесть по-прежнему проверяет validateInitData. Никакому обычному user.id из браузера не доверяем.

Store.authenticate может возобновить bearer только если его серверный Telegram ID совпадает с проверенным ID текущих initData. Повтор того же launch-proof при reload допускается только с уже действующей сессией того же владельца; отпечаток остаётся связан с этим владельцем. Чужой bearer не позволяет повторно использовать уже использованный proof другого пользователя. При свежих initData другого аккаунта создаётся сессия этого аккаунта.

Без initData live-клиент не загружает личные данные даже при наличии старого токена. Общий долговременный localStorage bearer удаляется; для reload используется sessionStorage и обязательная серверная сверка. Локальные данные и черновики привязаны к userId из проверенного серверного ответа; старые общие черновики не восстанавливаются в аккаунт. Локальный архив не смешивается с серверной историей. Существующие серверные заявки не переносятся, не удаляются и не превращаются в реальные.

При смене initData в открытом окне стирается личное представление, закрываются детали, сбрасываются права и запускается повторный вход. Сырые initData, захваченные из текущего native launch URL до навигации, приоритетнее возможного старого кеша SDK. При отсутствии launch URL используются данные SDK. Счётчик поколения сессии отклоняет запоздалые ответы старого пользователя. Отложенная запись черновика при переходе отключается. Версия URL клиентского JS обновлена для загрузки исправления после переоткрытия Mini App.

## Проверки

Новый WebKit tests/account-switch.e2e.cjs работает с настоящим локальным HTTP API, HMAC и PostgreSQL engine PGlite. Сценарий общего хранилища: менеджер A с legacy bearer → обычный B → поздний ответ A → reload B с тем же launch proof → возврат A с восстановлением только его черновика → запуск без initData. 25 проверок: раздельные заявки, грузовик/телефон, закрытие старых деталей, отсутствие у B административных прав, 404 на заявку A с bearer B, 403 на импорт B, отсутствие истории/профиля без proof. Telegram-транспорт заменён локальным mock; нет обращений к реальным заказам или отправок сообщений.

HTTP ACL-тест дополнительно проверяет переключение аккаунта с чужим сохранённым bearer, owner-bound resume, отказ replay другого proof и отказ live-входу без initData при наличии bearer. Полная регрессия и публичный smoke выполняются отдельно.

Сохранено ограничение свежести Telegram initData 5 минут при входе/перезагрузке. Если Telegram повторно использует старый launch payload, требуется закрыть и открыть приложение заново; уже открытая верифицированная сессия продолжает работать. Физическую смену аккаунта в iPhone Telegram после публикации должен проверить владелец.
