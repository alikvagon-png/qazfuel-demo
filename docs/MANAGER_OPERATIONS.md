# QAZFUEL: работа менеджера

В личном чате @QazFuelServiceBot отправьте `/admin` с ранее привязанного аккаунта менеджера. Другой пользователь не получает доступа к панели, данным клиентов или изменению настроек.

Панель: новые, подтверждённые, выполненные, отменённые, отклонённые и истёкшие заявки. Списки по 5 записей с перелистыванием. Карточка содержит полный номер, время UTC, место, объём, контакты и переход к клиенту. Подтверждение и отклонение доступны для новых заявок; завершение и отмена подтверждённой заявки требуют дополнительного нажатия. Завершение не изменяет первоначальное время и срок брони. Истёкшие заявки подтвердить нельзя.

## Ручные цены

`/price moscow 95 65.50` — пример формата, не реальная котировка. Используйте собственную проверенную рыночную цену.

Регионы: `moscow`, `moscow_oblast`. Топливо: `95`, `98`, `dt`.

`/price moscow 95 off` — удалить ручную котировку. При ошибке ввода команда ничего не меняет. Цена QAZFUEL = введённая рыночная цена минус 3 ₽/л. Размер скидки клиент не меняет. Ручная котировка действует 24 часа от сохранения, показывается с датой и источником «Ручная котировка менеджера», используется только при отсутствии свежего API. АИ-98 задаётся независимо. При отсутствии данных — «Цена уточняется». Команда не устанавливает цену задним числом для уже принятых заказов; окончательные условия согласовываются менеджером.

## Точки и повтор

В панели «Работа точек» закрытие/открытие требует подтверждения. Закрытая точка остаётся на карте с сообщением, кнопка бронирования и пункт выбора отключены. Сервер повторно проверяет доступность под блокировкой, существующие заявки не отменяет. Клиентская доступность обновляется каждые 30 секунд. Повтор заказа уже реализован: заполняет форму прежними данными, не создаёт заказ автоматически и повторно проверяет доступность.

## Уведомления

Новые изменения статусов реальных заявок создают постоянную очередь уведомлений клиенту в той же транзакции через PostgreSQL trigger. Подтверждение, отклонение, отмена, истечение и завершение содержат номер заявки и кнопку истории. Только верифицированный Telegram ID владельца является получателем. Предыдущие события до установки функции не рассылаются.

Проверка очереди каждую минуту, до 5 попыток с интервалом 5 минут. Блокировка бота клиентом может не позволить доставить сообщение: приложение остаётся источником актуального статуса. Семантика доставки at-least-once: при сбое между Telegram и фиксацией транзакции возможен повтор сообщения. Несколько работников используют SKIP LOCKED.

Одно напоминание менеджеру после 15 минут ожидания, только для новых реальных заявок с успешно отправленным первоначальным уведомлением. Не выполняется рассылка по старой истории. На бесплатном Render Web Service таймер не работает во время сна; обработка возобновится после пробуждения. Для гарантированных сроков требуется постоянно работающий worker/платный сервис, который этим обновлением не создаётся.

Секреты, webhook, менеджер и инфраструктурные планы не меняются. Миграция сохраняет данные. Добавлен статус completed; предыдущие клиенты должны получить новую версию интерфейса.

## Проверка

`npm test --prefix server`: PGlite выполняет настоящие SQL миграции, проверки прав, дедупликации, закрытых точек, ручных цен и их истечения, переходов, очереди уведомлений и напоминаний. Telegram в автоматических тестах заменён транспортным mock: это не подтверждение реальной доставки новых типов уведомлений. Предыдущие реальные проверки подтверждения/отклонения сохраняются. Дополнительно мобильные проверки WebKit и regression suite.
