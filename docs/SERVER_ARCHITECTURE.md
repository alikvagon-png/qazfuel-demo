# QAZFUEL: архитектура реального приёма заказов

**Статус: проектирование. Перечисленный сервер, база, авторизация менеджера и отправка уведомлений не реализованы и не запущены.** Текущий V3 — локальное демо. Ни один ресурс и платный тариф этой документацией не создаётся. Переход к реальному приёму требует отдельной реализации и проверки.

## Состав

Статический Mini App обращается по HTTPS к Node.js API. API хранит заказы в PostgreSQL, проверяет Telegram-авторизацию, применяет бизнес-правила и предоставляет отдельный интерфейс менеджера. Уведомления идут через транзакционный outbox после сохранения заказа. Сбой Telegram не должен отменять сохранение или создавать второй заказ. Текущий действующий бот, main и production-сервис не перенастраиваются автоматически.

Клиентские модели в `v3/core.js`: `kind=truck|delivery`, `status=pending|confirmed|cancelled`, `createdAt`, `pointId`, `liters`, `brand`, `plate`, `fuel`, `address`, `phone`, `comment`, `fullTank`. Это формат демо, не доверенный источник реального статуса. Записи legacy остаются локальной историей и никогда автоматически не импортируются как брони.

## PostgreSQL и инварианты

| Таблица | Ключевые поля и назначение |
|---|---|
| users | UUID, уникальный telegram_user_id BIGINT, минимальные данные профиля |
| sessions | хеш случайного идентификатора, user_id, expires_at, revoked_at |
| trucks | user_id, brand, plate; только собственные сохранённые машины |
| points | стабильный id из core.js, имя, lat, lng, страна; опубликованные оператором данные |
| orders | UUID, user_id, kind, status, created_at, expires_at, confirmed_at, point_id, fuel, liters nullable, full_tank, vehicle snapshot, address/phone/comment, quote_id, version |
| order_events | order_id, старый/новый статус, actor_id, actor_role, timestamp, reason, request_id; журнал без редактирования событий |
| idempotency_keys | user_id, key, request_hash, order_id, сохранённый результат; уникальность (user_id,key) |
| fuel_quotes | источник, регион, точная марка, RUB/л в decimal, рыночная цена, скидка, цена QAZFUEL, observed_at, fetched_at, expires_at |
| notification_outbox | order_id, event_id UNIQUE, получатель, retries, next_attempt_at, delivered_at |

Время только UTC/timestamptz; доверенное время — PostgreSQL. `created_at` присваивается сервером один раз, `expires_at=created_at+interval '24 hours'` для truck; для delivery срок брони не назначается. Запретить изменение created_at/expires_at на уровне БД триггером и ограниченными SQL-правами. Время подтверждения не продлевает бронь. Не использовать часы клиента для разрешения операций.

Truck: только ДТ, существующий point_id, допустимый объём, марка и номер обязательны. Delivery: только АИ-95/АИ-98/ДТ, адрес и нормализованный телефон обязательны, номер машины не требуется. Full tank означает неизвестное заранее количество (`liters=null`); не выставлять окончательную сумму до фактической заправки. Ограничения размеров строк и числовых значений проверяются повторно сервером и CHECK constraints.

## API и жизненный цикл

- `POST /auth/telegram`: проверка initData и выдача короткоживущей сессии.
- `GET /me/orders`, `GET /me/orders/:id`: только владелец, пагинация, авторитетный статус и serverNow.
- `POST /orders`: валидированный payload + Idempotency-Key; ответ 201 только после commit.
- `POST /orders/:id/cancel`: владелец, проверенный переход, optimistic version.
- `POST /admin/orders/:id/confirm`: только manager, серверная атомарная проверка срока.
- `GET /points`, `GET /prices?region=...&fuel=...`: публичные справочные данные без личных полей.

Создание: транзакция фиксирует заказ pending, событие и outbox. Confirmation: внутри одной транзакции условный UPDATE по `status='pending' AND expires_at>clock_timestamp()` с RETURNING; затем событие, outbox и commit. Использовать блокировку строки/проверку version для конкурирующих операций; ноль обновлённых строк означает конфликт/истечение срока, не успех. При повторном запросе подтверждения уже подтверждённый заказ возвращается без второго события. Отмена и подтверждение не должны успешно обгонять друг друга.

Истёкшая truck-бронь вычисляется при каждом чтении и записи. Фоновая задача может материализовать expired и отправить уведомление, но корректность не зависит от её своевременного запуска. Публичный статус «Забронировано» разрешён только после авторизованного события менеджера в серверной БД. Клиентский секундомер рассчитывается относительно serverNow; перезагрузка и повторное открытие не сбрасывают срок. Повтор заказа создаёт новый UUID и новое created_at после явного действия клиента.

## Telegram и сессии

Официальная инструкция Telegram проверена 30.10.2026: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app . Передавать сырой `Telegram.WebApp.initData` на backend; не доверять initDataUnsafe. Проверять hash через HMAC-SHA-256 по официальному отсортированному data-check-string, с производным ключом из bot token и WebAppData. Для Node crypto порядок аргументов: createHmac(algorithm, key). Сравнение хешей — постоянного времени после проверки длины и формата. Проверить auth_date: например, окно 5 минут и допуск часов 30 секунд — это предлагаемая политика QAZFUEL, не лимит Telegram. Не принимать дубликаты параметров и чрезмерный размер строки. Профиль распарсить и принять только после верификации. Сырой initData не логировать.

BOT_TOKEN только в серверном secret/environment. Сессию хранить через Secure HttpOnly cookie с подходящим SameSite для проверенного WebView-контекста; для cookie-auth обязательны Origin/CSRF-проверки. На отдельном API-домене проверить third-party cookie ограничения Telegram/Safari и выбрать короткоживущий bearer в памяти, если требуется; не класть долгоживущий bearer в localStorage. Настроить точный allowlist origins, не credentials + wildcard. Ротация и отзыв сессий, лимиты /auth и /orders по пользователю/IP, защита повторного использования initData, лимит тела, безопасные ошибки.

## Администрирование и приватность

Manager/admin роли назначает оператор на сервере; роль не берётся из client payload или Telegram username. Для админки — отдельная проверенная авторизация с MFA, RBAC и журнал действий. Пользователь не может подтвердить свою бронь или прочитать чужой UUID. Применять параметризованные запросы и least-privilege DB role.

Телефон, адрес, номер машины и координаты — ограниченный доступ; TLS в транзите, защита БД/backup, маскирование в логах и отсутствие аналитики с личными payload. Геолокация необязательна, только после согласия; не передавать её ценовым API. Предлагаемая retention-политика: удалять ненужную точную геолокацию после исполнения, сокращать персональные данные старых заявок по утверждённому сроку; конкретный срок и правовые обязательства согласовать до production. Пользователь должен иметь возможность удалить сохранённый грузовик и запросить удаление данных. Демо localStorage не является резервной копией реальных заказов.

## Цены

Серверный адаптер к источникам решает CORS и хранит секреты, но не исправляет пустые/устаревшие данные. Результаты реальных запросов см. `PRICE_SOURCES.md`. Обязательны точная марка, регион, источник, observed_at и RUB/литр. Отбрасывать неизвестную валюту/единицу, будущую дату и превышение допустимого возраста (предлагается 24 часа для оперативной цены). Не заменять регион национальной средней и не считать generic premium доказанной маркой АИ-98. Скидка 1–3 ₽/л, default 2, задаётся сервером; числовые расчёты decimal/копейки. Отсутствие валидной котировки возвращает unavailable, без выдуманного итога. Ручная цена — только через менеджера с источником, регионом, датой и аудитом. TTL кэша, таймаут, ограниченный retry/backoff, rate limits поставщика и видимая атрибуция обязательны.

## Проверки перед реальным запуском

Реальные интеграционные тесты PostgreSQL: idempotency, разные payload с одним ключом (409), гонка двух подтверждений, подтверждение на границе 24 часов, отмена против подтверждения, неправильный hash/auth_date, чужой заказ, отказ Telegram после commit, восстановление backup. E2E на iOS Telegram и Safari с настоящим тестовым ботом. Отдельный staging, миграции, health/readiness endpoints, наблюдаемость без PII, резервное копирование с проверенным восстановлением. Ни одна из этих серверных гарантий не заявляется реализованной в локальном preview.
